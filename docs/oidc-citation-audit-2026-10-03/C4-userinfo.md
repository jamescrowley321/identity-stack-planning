# C4-userinfo: UserInfo citations (§5.3.1 / §5.3.2 / §5.3.4)

Checkout: im-audit @ 1e3b6a6. Spec: openid-connect-core-1_0.txt (errata set 2).

## 1. Spec re-verification

- **§5.3.1 (txt:1787)**: "The Access Token ... MUST be sent as a Bearer Token, per Section 2 of [RFC6750]." / "It is RECOMMENDED that the request use the HTTP GET method and the Access Token be sent using the Authorization header field." Bearer is a MUST. GET plus the header is only RECOMMENDED.
- **§5.3.2 (txt:1805, HTML anchor `#UserInfoResponse`)**: "The sub (subject) Claim MUST always be returned in the UserInfo Response." / "The sub Claim in the UserInfo Response MUST be verified to exactly match the sub Claim in the ID Token; if they do not match, the UserInfo Response values MUST NOT be used." It also says that if the response is signed, "MUST contain the Claims iss ... and aud".
- **§5.3.4 (txt:1859, anchor `#UserInfoResponseValidation`)**: three steps only: (1) TLS cert check per RFC 6125, (2) decrypt if `userinfo_encrypted_response_alg` is registered, (3) "If the response was signed, the Client SHOULD validate the signature according to JWS". It says nothing about `sub`.
- **2014 vs errata 2**: the sub-match sentence and the RECOMMENDED GET/header wording are the same in both, and the section numbers did not change, so every finding holds under either edition. The only edition differences are the RFC citations (7231 instead of 2616, and the Registration date). They don't matter here.
- Findings (a), (b) and (c) are confirmed.

## 3. Behavior: sub match (§5.3.2 MUST)

| | sub-match when caller supplies expected sub | when not supplied | missing `sub` | `application/jwt` | mismatch error type |
|---|---|---|---|---|---|
| py | `get_userinfo` → `validate_userinfo_sub` (sync/userinfo.py:70, aio:70) | skipped silently | rejected **only** if expected_sub set (#773, `UI-003-missing-sub` KnownGap) | returns `raw` with **no sub check even when expected_sub is set** (userinfo_logic.py:101 `response.raw is not None` → early return) (#774) | magic string `"UserInfo sub mismatch: ..."`. The runner asserts a substring (test_spec_http_vectors.py:133) |
| go | `WithSubjectValidation` (options.go:44) | skipped silently | always rejected (`RequestError`) | rejected (`RequestError`) | typed `*SubjectMismatchError` + `ErrSubjectMismatch` |
| rust | `fetch_with_subject` (mod.rs:86) | `fetch` skips silently | always rejected | rejected | **`IdentityError::Validation(String)`**, a magic string. The runner matches `msg.contains("sub mismatch")` (rust/tests/spec_http_vectors.rs:181). This violates the typed-errors rule |

**Opt-in in all three.** No library API combines ID Token validation with UserInfo. The only place that wires them together is `conformance/app.py:_fetch_userinfo`, which passes the validated ID token's sub. Its FAPI2 resource-call reuse (app.py:1335-1365) relies on `expected_sub=None`, because there it is a plain sender-constrained GET with no OIDC meaning.

**Is caller-optional a MUST-enforcement gap?** It is partly unavoidable, but the current shape fails open.
- The MUST binds the *Client* and is conditional on there being an ID Token to compare against. A bare `fetch(endpoint, access_token)` cannot know that sub. A resource server that only holds an access token, which is a common Cognito API-backend pattern, has no ID token at all. Making the expected sub a required non-null argument would therefore misstate the spec for those callers.
- The policy problem is that skipping the check is **silent and the default**. It reads like the "hardening option" pattern applied to a spec MUST. A caller who holds an ID token and forgets the argument gets an unchecked response and no signal. Under the "spec MUST = unconditional, no off switch" rule, the closest compliant shape is to make the choice explicit and impossible to omit: the subject argument is mandatory and is either an expected sub or an explicit "no ID token for this access token" marker. A mismatch can then never be skipped by accident, and the access-token-only case stays legitimate. This is a breaking API change in all three languages (py `UserInfoRequest`, go `Fetch` signature, rust `fetch`/`fetch_with_subject`). Rust has no users. For py and go it needs James's call, so it is proposed as a decision-gated story rather than a fix.
- **Real fail-open bug in py today (#774)**: if the caller *did* supply `expected_sub` and the OP answers `application/jwt`, py returns success with no check. That is a caller-requested MUST check being silently dropped. It is BEHAVIOR and a spec MUST, py only. Go and Rust fail closed.
- py #773 (no-sub accepted without expected_sub) is a §5.3.2 MUST gap ("sub MUST always be returned"), already filed. It is BEHAVIOR, py only.

**Cognito impact**: Cognito `/oauth2/userInfo` returns JSON whose `sub` equals the ID token `sub` (the user-pool UUID). The doc fixes have no impact. #773 has none either (Cognito always returns sub). #774 has none (Cognito never serves application/jwt). The explicit-subject API story would force existing py callers to add an argument. identity-stack/backend does not call `get_userinfo` (grep: no hits).

## 4. §5.3.4 step 3 (signed UserInfo SHOULD be validated), brief

It applies to `application/jwt` responses that are signed (§5.3.2 says the claims "are returned in a JWT and the content-type MUST be application/jwt"). Encrypted-only responses are possible too. Per language:
- **py**: returns the JWT string in `UserInfoResponse.raw` with no signature, `iss`/`aud`, or sub check, and the caller has to do all of it. This is a SHOULD not done, plus the #774 MUST hole on sub.
- **go / rust**: refuse `application/jwt` with a "not supported" error. That is compliant, because no unverified claims are ever used.
- No vector covers `application/jwt`. Full signed-UserInfo support is new scope and not proposed here. The minimal fix is for py to fail closed when `expected_sub` is set (#774).

- Given capabilities.md:111, then the label reads §5.3.2 and matches the `#UserInfoResponse` anchor.
- Given capabilities.md:110, then it states Bearer as the spec MUST (§5.3.1 → RFC 6750 §2), and GET + `Authorization` header as the implementations' contract (RECOMMENDED by §5.3.1), linked to `#UserInfoRequest`.

Tests/vectors: none. Behavior is unchanged.

### S2 `fix(py): fail closed on application/jwt UserInfo when expected_sub is set` (= #774), size S, no deps
Scope: py/src/py_identity_model/core/userinfo_logic.py (`validate_userinfo_sub`), plus unit tests in test_sync/aio_userinfo.py and a new vector.
- Given `expected_sub` is set and the OP returns 200 `application/jwt`, when `get_userinfo` runs, then the result is unsuccessful, never `raw` with no check. This is the minimal fix: decoding or verifying the JWT is out of scope.
- Given `expected_sub` is None and the response is `application/jwt`, then the current `raw` passthrough is unchanged. Changing that is a separate decision tied to S4.
Vector: add `UI-00x userinfo-jwt-with-expected-sub` → reject to spec/vectors/userinfo.json plus a fixture. Go and Rust already reject, so their runners need only the new id wired in. Verify that the Go and Rust error shape satisfies whatever `expect.error` key is chosen (for example `unsupported_response_type`). Cognito: no impact.

### S4 (decision-gated, needs James) `feat!: make the UserInfo subject decision explicit in py, go and rust`, size L, depends on S2 and S3 (and #773)
Rationale: the §5.3.2 MUST is skipped silently by default in all three. The library can't know the ID token sub, so this story doesn't make the sub required. Instead the caller must choose, which removes the silent default.
Scope: py `UserInfoRequest` (replace `expected_sub: str | None = None` with a required `subject: ExpectedSubject | NoIdToken` or similar), go `Fetch(ctx, endpoint, token, subject SubjectCheck, opts...)`, rust `fetch(token, Subject)` (drop `fetch_with_subject`), conformance/app.py call sites (the FAPI2 resource reuse passes `NoIdToken`), examples, docs, and spec/capabilities.md:111 (drop "When an expected `sub` is supplied").
- Given a caller who omits the subject argument, then the code does not compile (go/rust) or raises at construction (py).
- Given `ExpectedSubject(s)`, then every response path (JSON, jwt, missing sub) is either checked or rejected. Nothing is returned unchecked.
- Given `NoIdToken`, then behavior equals today's no-expected_sub path.
Vectors: the `input` schema gains an explicit subject mode, and UI-001/004-007 declare `no_id_token`. Breaking for py and go users, with a major or minor bump per release rules. Cognito: callers have to add one argument. Behavior with a matching sub is unchanged.
Alternative if James declines: keep opt-in and document in capabilities.md that the sub match is the caller's §5.3.2 obligation. S1 already improves that wording.

Not proposed: signed/encrypted UserInfo verification (§5.3.4 step 2/3). This is new scope. Go and Rust refuse jwt, and S2 closes the py fail-open.
